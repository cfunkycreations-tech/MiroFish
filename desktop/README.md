# MiroFish Desktop · Windows `.exe`

Package MiroFish (Vue 3 frontend + Flask backend) as a double-click Windows desktop app.

```
desktop/
|-- launcher.c            native launcher (C) -> compiled into MiroFish.exe
|-- app.rc / app.manifest icon, version info, DPI and long-path manifests
|-- app.py                desktop runtime: user data directory, Flask + static assets, pywebview window
|-- Setup.bat             first run of the online build: create the Python runtime and install the dependencies
|-- fetch_sources.py      fetch the assets: Windows dependencies, embeddable Python, icon, exe
|-- build.py              assemble the installer (offline / setup modes)
|-- verify_exe.py         verify the PE: GUI subsystem, icon resources, dependent DLLs
|-- icon_source.png       the master app icon (1024^2)
|-- icon.ico / icon.png  generated by fetch_sources.py (multiple sizes; small sizes get an enlarged subject)
├── requirements-desktop.txt
├── version.txt
`-- tests/test_desktop.py unit tests for the launcher and the settings API
```

## Builds

| Mode | Size | Notes |
|------|------|------|
| `--mode offline` | about 1 GB (zip about 500 MB) | bundles Python 3.12 and every dependency; ready to run after extraction, fully offline |
| `--mode setup` | about 34 MB (zip 16 MB) | bundles `uv.exe`; the first run has `Setup.bat` create the runtime and download the dependencies |

Both modes share the same directory layout; `MiroFish.exe` looks in this order:

```
runtime\venv\Scripts\pythonw.exe     <- the virtual environment created by Setup.bat
runtime\python\pythonw.exe           <- the embeddable Python bundled in the offline build
the MIROFISH_PYTHON environment variable  <- for development
```

## Runtime behavior

1. Data directory: `%APPDATA%\MiroFish` (override with `MIROFISH_HOME`)
   - `.env` is created from the template on the first run, with a random `SECRET_KEY`
   - `uploads\` documents, graphs, simulations, reports
   - `logs\desktop.log` the full log (so issues can be diagnosed even with no console after packaging)
2. Backend: `waitress` listens on `127.0.0.1:<random free port>` and serves both
   * the built frontend (with the vue-router history deep-link fallback)
   * `/api/*` and `/health`
   so the desktop build has no CORS and no hard-coded port.
3. Window: `pywebview` (WebView2) loads `http://127.0.0.1:<port>/`;
   when no keys are configured yet, the frontend jumps to the `/settings` page automatically.

## Building locally (Linux / macOS / Windows all work)

```bash
# 0) Requirements: Node 18+, Python 3.10-3.13
cd frontend && npm ci && npm run build && cd ..

python -m pip install uv ziglang pillow      # zig cross-compiles the .exe
python desktop/fetch_sources.py --build-dir build
python desktop/verify_exe.py build/MiroFish.exe

python desktop/build.py --mode setup   --out dist --zip
python desktop/build.py --mode offline --out dist --zip \
    --wheels build/wheels-win312 --embed build/embed312
```

What `fetch_sources.py` does:

- `uv pip install --python-platform x86_64-pc-windows-msvc` to fetch the Windows dependencies
- pull the official **embeddable CPython 3.12** out of the PyPI `python-embed` package
- generate a multi-size `.ico` from `icon_source.png` (the subject is enlarged below 48px)
- cross-compile `launcher.c` with `zig cc` (GUI subsystem + icon resources)

## CI

`.github/workflows/desktop-build.yml` builds natively on `windows-latest`:

- pushing a `v*` tag -> builds both installers and attaches them to the Release
- `workflow_dispatch` -> manual trigger, artifacts land in the Actions artifacts

## Known limitations

- only **x64** is released; ARM64 Windows can run it from source.
- when WebView2 is missing (rare), use `MiroFish.exe --browser` in your default browser.
- a simulation calls the LLM / Zep cloud services over the network; offline you can only browse existing results.
